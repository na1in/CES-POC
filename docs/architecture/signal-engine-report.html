CES Signal Engine — Verified Reference Report

Every formula, threshold and dependency below was read from the current code on nalin-dev just now (not copied from the design docs) and cited to a file and line so you can check it yourself. Where the code disagrees with docs/Step3_Feature_Signals.md or CLAUDE.md, that's called out explicitly.

Is it really 19 signals?

Short answer: it's 20, and the code computes all 20 correctly — the "19" label in the docs is stale.

Every category's formulas check out against the code (see the tables below). But counting the individual signal computations actually listed in docs/Step3_Feature_Signals.md and in CLAUDE.md's own breakdown gives 4 + 6 + 2 + 4 + 4 = 20, not 19 — Category 2 (Amount & Variance) is even headed "(7)" in CLAUDE.md while only 6 signals are listed under it. The payment_signals table itself has 37 persisted columns for these 20 logical signals (several, like Name Similarity, store multiple breakdown fields). Nothing is missing or double-counted in the code — this is a documentation/counting drift, not a computation bug, and it's worth fixing in the docs the next time they're touched.

The flow you're following

Yes — run_signal_engine() follows a real 3-wave order, and it's reproduced exactly below (not the idealised 4-level dependency map in the design doc, which groups a few signals differently than the code actually does). Only 2 of the 20 signals actually need concurrency

Name Similarity (may call an LLM) and Duplicate Match (a DB query) are the only I/O-bound signals, and they're the only two run with asyncio.gather() (signal_engine.py:73). Everything else is plain, fast Python — the "3 waves" are mostly an ordering convenience for readability, not a strict necessity: several "Wave 3" signals (Risk Flags, Account Status, Payment Method Risk, Balance Snapshot) don't depend on anything computed in Wave 1 or 2 and could run at the very top with no change in behaviour.

Verified finding: several "configurable" thresholds never reach the signal engine

Changing these values in Admin → Configuration currently has no effect on signal computation

run_signal_engine(payment_id, payment, customer, policy, db) takes no thresholds argument, and nothing in signal_engine.py or services/signals/*.py queries configuration_thresholds — confirmed by search, zero matches. Every tolerance the signal-computation functions use is a hardcoded Python default instead:
