CES — Customer Exception System AI-assisted resolution of unidentified insurance payments · architecture overview

1 · Business Context

The problem. Payments arrive that the ledger cannot automatically apply — a misspelled sender, a missing policy number, an amount that doesn't match the premium. These land in a suspense account and reach an analyst as a flat, arrival-ordered list with no supporting context. For each case the analyst opens customer records, policy data and payment history in separate screens and reconstructs the evidence by hand. Triage quality depends on individual experience, two analysts can reach different conclusions on the same payment, and the reasoning behind a decision is never captured.

What CES changes. Every payment is scored against 19 engineered signals, classified into one of 5 exception scenarios, and delivered to a queue ranked by confidence where each case opens as a pre-built dossier — signal bars, algorithm-level match breakdown, written rationale and a full audit trail. The analyst's work shifts from assembling evidence to judging it.

The governing constraint: a deterministic rule engine owns every decision and the LLM only explains it. Nothing auto-applies money — every payment lands in a human review queue regardless of confidence.

3 · Processing Pipeline

Five stages. Stage 1 always succeeds — the payment is persisted as RECEIVED before any processing is attempted — so a pipeline failure is never data loss.

The five exception scenarios

#ScenarioTriggerOutcome
5Duplicate Payment Evaluated first on every payment. 3 exact fields + $2 tolerance, 72-hour window Balance > 0 → HOLD; balance = 0 → ESCALATE
1Strong Policy Match Policy number present, name ≥ 75%, variance ≤ 2% HOLD; recommends APPLY when name > 90% and no risk flags
2Customer Match, No Policy Customer match ≥ 90%, or < 90% with 2+ supporting signals Always requires human approval
3High Amount Variance Match found but variance > 2% Tiered: 2–15% HOLD; 15–50% special cases; > 100% ESCALATE
4No Matching Customer All matching failed Third-party check first, otherwise ESCALATE

5 · Features

Functional

Hybrid name matching

Jaro-Winkler (50%) + Levenshtein (30%) + Soundex bonus (10%). Below 70% or above 92% resolves deterministically with no model call; only the gray zone is adjudicated by the LLM.

19 signals, 3 dependency waves

Matching, amount & variance, temporal, risk & fraud, duplicate detection — with parallel fan-out inside each wave and a full snapshot written before routing.

Deterministic scenario routing

Scenario 5 short-circuits first; scenarios 1–4 follow an explicit if/else ladder. No model involvement in the decision itself.

Ranked approval queue

Sorted by confidence descending, filterable by band, scenario, recommendation and method. Stat tiles double as filters.

Escalation & SLA tracking

Analyst → investigator handoff preserves full case history; sender outreach starts an SLA timer whose breach surfaces on the director's exception dashboard.

Threshold governance

Change request → staged simulation → director approval → deploy → rollback, with full version history. Thresholds are read at decision time, never hardcoded.

Case annotations & documents

Case notes, override reasons and investigation notes; document upload with soft-delete only.

Decision attribution & analytics

Every closure records AI-vs-human attribution, feeding override rate by confidence band and the audit-ready compliance export.

Non-functional

Financial correctness

All monetary values as integer cents. Every state transition in a single transaction against an append-only audit log.

Fault tolerance

3 attempts with 1s/3s backoff. Retryable: DB timeouts, deadlocks, LLM rate limits. Non-retryable: constraint and validation errors. Exhausted → PROCESSING_FAILED, reprocessable via API.

Graceful model degradation

All three LLM touchpoints fall back to deterministic output, so no provider outage can fail a request.

Auditability

Immutable per-payment signal snapshot means any recommendation replays against the exact feature state that produced it — which is also what makes threshold simulation possible.

Test coverage

393 pytest (rollback-only DB fixtures, --live-llm toggle) and 38 Playwright E2E across 6 spec files.

Role-based access

Four roles with server-side guards; UI affordances gated to match, so no role sees an action the API would reject.
